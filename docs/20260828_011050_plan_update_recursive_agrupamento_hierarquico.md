## 1. What This Update Had to Reconcile

The evaluation document (`20260827_111015_…`) established that the LexML maintainers' change to `AgrupamentoHierarquico` achieves what the project needs, by a better route than our own proposal. It also proposed a revised cycle structure. But it was written as an **analysis**, standing alongside the plan rather than inside it — and in three places its assumptions had already drifted from the repository:

| The evaluation said | The repository actually had | Resolution |
|---|---|---|
| patched schemas as a fixture copy under `tests/fixtures/schemas/` | `lexml-proposed/`, generated by `scripts/build_proposed_schemas.py`, committed in `a1b3124` | use `lexml-proposed/` — **verified to change nothing about the proposal** (§3) |
| a third "refined" schema set so `interleaved_children` probes `True` | no such directory; the refinement is *ours*, not the maintainers' | not produced — the refinement is forwarded upstream only (§3) |
| Cycle 6b "possibly droppable", "recommendation" | plan still listed it as a deliverable | dropped outright, by user decision (§4) |

So the task was not transcription. It was deciding, for each of the evaluation's recommendations, what the plan should now *oblige* — and keeping the distinction between the maintainers' change (authoritative) and our suggestions (offered upstream) visible throughout.

## 2. Method

1. **Read in the order CLAUDE.md prescribes** — `STATUS.md`, then the plan, then the cycle reports — so that what was *actually built* framed what could be amended.
2. **Verify rather than assume.** Two claims were load-bearing and both were checked by command, not by reading prose: what `lexml-proposed/` actually contains (§3), and whether the suite was green (§6).
3. **Ask only what verification could not settle.** One decision genuinely needed the user (§4).
4. **Amend visibly, never silently.** Every change carries an ID (A-R.n), and reversed decisions are struck through with reasons rather than deleted — the plan is amendable, not disposable.
5. **Leave delivered records alone.** Cycle reports state what was built; they are not rewritten when the plan moves.

## 3. The Load-Bearing Verification: does `lexml-proposed/` alter the proposal?

The user's constraint was explicit: *the LexML change proposal from the evaluation document must prevail; folder structure is fine to adjust as long as it does not change the proposal.*

That is a factual question, so it was answered factually. Diffing the two schema generations, normalising line endings:

```bash
diff <(tr -d '\r' < lexml/lexml-base.xsd) <(tr -d '\r' < lexml-proposed/lexml-base.xsd)
```

The **entire** substantive difference:

```xml
-  <xsd:sequence>
-    <xsd:group ref="LXhierCompleto" minOccurs="1" maxOccurs="unbounded"/>
-  </xsd:sequence>
+  <xsd:choice minOccurs="1" maxOccurs="unbounded">
+    <xsd:group   ref="LXhierCompleto"/>
+    <xsd:element ref="Agrupamento"/>
+    <xsd:element ref="Bloco"/>
+  </xsd:choice>
```

Everything else is a generated-file header comment and one comment-terminator reflow. The other two schemas differ **only** by that header. This is byte-for-byte the change in §2 of the evaluation document.

**Conclusion:** using `lexml-proposed/` is purely a repository-layout matter. The proposal is untouched. The evaluation's `tests/fixtures/schemas/` wording predated the directory's existence; pointing the plan at the real directory records what was actually built.

**Corollary, and the reason this mattered.** The evaluation's §3.7 **refinement** — moving `AgrupamentoHierarquico` out of the `hierarchy` base into the extension `choice`, which would remove the ordering wart — is **ours, not the maintainers'.** It is correctly absent from `lexml-proposed/`. Building against it would have meant building against a schema nobody has proposed but us. So:

> The emitter is built against the maintainers' change **as written**, and absorbs the ordering constraint (plan §5.4 C1). The refinement is forwarded upstream as a suggestion (plan §11.2 item 4), with its verified evidence and an honest statement of its wider blast radius. `interleaved_children` therefore probes `False` against **both** generations present, and no third schema set is produced.

This is the single most important decision in the update, and it is what makes the maintainers' proposal prevail in the sense the user asked for.

## 5. The Amendments, and the Reasoning Behind Each

Nine amendments, A-R.1 … A-R.9, listed in full in plan §14 and STATUS.md. The reasoning that is not obvious from the summaries:

### A-R.1 — §2.1 stops being absolute

§2.1 (*"`OpenStructure` cannot nest"*) is the empirical foundation of the entire design; it is why hierarchy went out-of-band into the `id` path. It could not simply be deleted — it remains **true of the shipped schemas**, and the default emitter depends on it. Nor could it stand unqualified — it is **false of the proposed schemas**.

It was therefore **re-scoped, not replaced**: the table is now a statement about a named schema generation, with an amendment note at the head and *two* consequences stated side by side — out-of-band hierarchy for the flat emitter, in-band for the nested one. New §2.10 records the maintainers' change; new §2.11 records that capabilities are probed rather than assumed.

That both consequences are live simultaneously is exactly why the plan now carries two emitters, and saying so in §2.1 is what keeps the rest of the plan coherent.

### A-R.2 — the capability probe, and *when* it lands

The evaluation placed the probe in a "Cycle 0 addendum". Cycle 0 is **complete**, and reopening a complete cycle to add code nothing yet consumes would make its 107-test report ambiguous about what was delivered when.

Resolution: the addendum is written into Cycle 0's section of the plan **for locality** — that is where a reader looks for the harness — but explicitly **scheduled to land with Cycle 5b**, the first cycle that needs it. STATUS.md shows this as a distinct `0+` row in the *not started* state, so no delivered figure is disturbed.

The addendum also carries the amendment that the §2.1 matrix cases gain a `requires` field and **skip rather than fail** when a capability is absent — the mechanical consequence of A-R.1.

### A-R.3 / A-R.4 — the nested emitter and its three constraints

New plan §5.2 (the emitter) and §5.4 (the constraints), plus new Cycle 5b. The constraints are stated as *measured against `lexml-proposed/`*, not asserted, because two of them are counter-intuitive enough that a future reader will doubt them:

1. **Subsections precede own prose.** XSD extension semantics append the new `choice` after the inherited sequence, so document order is *rejected*. This is the genuine wart, and it costs the property that made flat output trustworthy to hand-inspect. Its consequence is pushed into the segmentation contract: **order comes from `Rotulo` or a recorded source index, never from sibling position.**
2. **Every `AH` needs a non-`AH` child** — and an empty `<Agrupamento/>` is *also* invalid, so the escape is `<Bloco nome="vazio"/>`. The evaluation left this as an open decision between three options; the plan now **decides it** (option A), with the two rejected alternatives and their costs recorded.
3. **Prose always needs an `Agrupamento` wrapper** — bare `<p>` under an `AH` still fails, and this is row E of the matrix, which looks like it should have flipped and did not.

### A-R.5 — the oracle becomes three-way

Segmentation gains `segments_from_nested_xml()` alongside the existing id-path reader, and agreement becomes **model / flat XML / nested XML**. The nested reader parses no `id`s at all, which the plan makes testable by mutating every `id` in a nested document and asserting the segments are unchanged.

**Rule A is scoped rather than dropped** (see A-R.6 note in §9.2): required of the flat emitter, structurally guaranteed by the nested one, where a missing ancestor is a malformed tree instead of a silently truncated breadcrumb. Deleting it would break the flat emitter; leaving it unqualified would demand machinery guarding a bug that cannot be expressed.

### A-R.6 — two withdrawals

**Cycle 6b** is dropped. The emitter existed only because nesting was otherwise unreachable; §2.10 removes that premise, and synthesising `Artigo`s from a parecer's sections is precisely the misreading Cycle 4's quotation guard exists to prevent — committed deliberately, on output. Its round-trip reader is retained and relocated to Cycle 7, where it becomes more valuable: with two emitters in play, it proves they agree. Reinstatement conditions are recorded rather than deleted.

**Our own §11 proposal** is withdrawn. §11 becomes *Engagement with the LexML Community*: §11.1 why ours was inferior (we attacked `blocksreq`; `AgrupamentoHierarquico` was **already** recursive and `PartePrincipal` already accepted it — recursion was never missing, prose-bearing leaves were), §11.2 the reply endorsing theirs, §11.3 the ship sequence. The original text survives in `docs/20260801_142630_…` §6, and §13 says so.

### A-R.7 — a naming ambiguity the change introduced

With two `generico` emitters, `route=generico` in §4.4 became ambiguous. A note now states plainly: **routing is about what the document *is*; rendering is about how it is written out.** The route table is identical under both emitters, and no route changed.

### A-R.8 / A-R.9 — annexes, CLI, regression

Annex bodies may use the nested form (`port_mf_277`'s 130-entry `ANEXO ÚNICO` gains real structure). `--emitter=generico-aninhado`, a new `capabilities` command, nested goldens, cross-emitter equivalence in the regression suite — and the requirement that anchors the whole opt-in design:

> **The suite must stay green against `lexml/` alone.** With `lexml-proposed/` absent, nested tests skip with a reason and nothing fails. The parser's correctness must not depend on an unreleased schema.

### Two new cross-cutting invariants

§9.2 gains **#11 cross-emitter equivalence** (identical text, identical segment URNs — choosing a rendering must never change what the document *says* or how a segment is cited) and **#12 capability honesty** (no code assumes a schema generation).

## 6. What Was Deliberately Left Alone

Restraint is part of the record; each of these was considered and rejected.

| Untouched | Reason |
|---|---|
| `src/`, `tests/`, `tests/golden/` | A plan revision is not a cycle. `788 passed` before and after — verified, not assumed. |
| `lexml/` | Byte-identical to upstream, always. That is what makes drift detectable. |
| `lexml-proposed/`, `build_proposed_schemas.py` | Already correct; `--check` reports current. |
| Cycle 0/1/2 specs, reports, changes files | Reports state what was actually built. The convention is that they are **not rewritten** when the plan moves; the qualification goes in the plan and the revision changes-file. |
| Amendments A-0.1 … A-2.4 | Cycle findings, still true. Listed separately from the A-R.n series in STATUS.md so the two kinds do not blur. |
| §0 ratified decisions | None reversed. The four concern routing, jurisprudence scope, LLM support and the §7.1 table; the schema change touches none. |
| Cycles 1, 2, 3, 4, 5 | Genuinely unaffected — ingestion, metadata, URN, profiles, front/back matter, hierarchy inference and the flat emitter are all schema-generation-independent. |

That last row is the substantive finding of this update: **nothing already built was invalidated.** Plan §11 had predicted *"a schema improvement costs us one emitter, not a rewrite"*. It cost one new emitter and *removed* another — the prediction held, with the correction that the emitter targets `AgrupamentoHierarquico` rather than the recursive `Agrupamento` we had assumed. This is the payoff of the rendering-agnostic model in §3.1, and it is worth noting that the payoff was **designed for and then collected**, not lucky.
