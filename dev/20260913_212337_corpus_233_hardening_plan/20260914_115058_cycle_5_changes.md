## Guarding against a vacuous pass

A cycle that changes no behaviour has no regression signal of its own, so the
new assertions were checked for the failure mode where they cannot fail.

**One real defect was found and fixed during implementation.** In
`test_an_all_bad_batch_writes_nothing_and_exits_one` the first draft read:

```python
assert _written(out_dir) == [] if out_dir.exists() else True
```

which parses as `assert (x == [] if cond else True)` — a conditional
*expression*, not a guarded assertion. Whenever the output directory does not
exist the whole expression evaluates to `True` and the assertion cannot fail.
That is the common case in this very test, because nothing succeeded and `-o`
creates its directory lazily, so the assertion was passing vacuously on every
run. Rewritten as:

```python
assert not out_dir.exists() or _written(out_dir) == []
```

with a comment recording the trap. This is precisely the risk the cycle spec's
§7 named, caught in the cycle that named it.

Two structural guards were built in from the start:

- `test_an_all_good_batch_exits_zero` is the converse of every exit-1
  assertion in the module. Without it, a `parse` that always exited 1 and always
  wrote 20 files would satisfy the rest.
- `test_the_batch_fixture_is_what_it_claims` asserts the fixture's own
  cardinality and name-distinctness, so the central count cannot be wrong for a
  reason unrelated to the guard under test.
