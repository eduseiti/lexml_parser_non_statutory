## 2. Reconciliation — what the plan assumes vs. what exists

Cycle 5's deliverable text is four clauses. Measured against the tree, they are
in very different states, and that is the substance of this reconciliation.

| Plan clause | Reality |
|---|---|
| "deliberately corrupt, truncated, empty and wrong-format documents in `tests/fixtures/`" | **Already delivered**, by predecessor Cycle 8. `corrupt_docx` (not a ZIP), `truncated_docx` (valid ZIP, no central directory), `zip_that_is_not_a_docx` (valid OPC, no `word/document.xml`), plus a zero-byte `.docx` and an unsupported-suffix case inline in `test_robustness.py` |
| "a batch of 200 with 5 bad documents writes 195 files, reports 5 failures and exits 1" | **Not covered.** The nearest test, `test_robustness.py::test_one_bad_file_does_not_abandon_the_good_ones`, runs **3** documents with `--format=json` and **no `-o`** — it counts `"urn"` occurrences in stdout, never a written file. Nothing in the suite asserts the *written-file count* of a mixed batch, which is precisely the §1.5 silent-loss mode |
| "and the same for `corpus`" | **Largely covered** by `test_corpus_report.py`: isolation at 16 documents, `--stop-on-error`, an all-bad corpus that still reconciles. What is missing is the *multi-failure* arithmetic (every existing test uses exactly one bad document) |
| "a documented resumability story" | **Entirely absent.** No `resum*` token exists in `src/`, `tests/` or `docs/`. No code path implements skip-on-existing |

Three questions were put to the user; all three answers are binding.

### Q-1 — the fixtures already exist. What should this cycle do?

**Answer: reuse them; add only what is missing.** The deliverable is treated as
discharged by Cycle 8 and recorded here as scope overlap. `degenerate.py` is
**not modified** — five other test modules import it, and a second fixture
module for the same shapes would be a second source of truth that drifts.

Consequence: this cycle writes **no new fixture builders**. The batch tests
compose the existing ones.

### Q-2 — how far should the resumability story go?

**Answer: document and test the current behaviour.** No `src/` change, no new
CLI flag. The cycle asserts what re-running actually does and states plainly
which half of the plan's "safe and cheap" holds.

**This was measured before the spec was written, not assumed:**

```
run 1 → 1 file, sha256 X, exit 0
run 2 → 1 file, sha256 X, exit 0      (byte-identical)
run 3 → 1 file, sha256 X, exit 0      (byte-identical)
```

and on two sources sharing one URN, three consecutive runs into the same
directory produce the **same two filenames** each time — the disambiguated
`…_b.xml` does not accumulate `_b_b`, `_b_b_b` suffixes. At full scale, two
runs over all 15 samples both produce 16 files.

So: **safe is true and testable; cheap is false.** Re-running re-renders every
document. The spec commits to saying so rather than to implementing the flag
that would make it true.

### Q-3 — what batch scale?

**Answer: small batch, exact arithmetic.** ~20–30 documents with 5 bad ones,
asserting exact counts. The property is scale-independent — 195 of 200 and 20
of 25 test the same guard — and the suite is 81 s today, which is a budget
worth keeping. The plan's "200" is read as illustrative of the *shape*, not as
a required cardinality; recorded as amendment **A-5.1**.

### Non-blocking decisions (mine, recorded not asked)

- **New module** `tests/regression/test_batch_robustness.py` rather than
  extending `test_robustness.py`. The existing module is unit-scoped and
  per-document; this cycle's assertions are batch-scoped and write to disk,
  which is what `tests/regression/` holds.
- `_run` helper copied verbatim from `test_corpus_report.py`, as that module
  copied it from `test_cli_corpus.py`. Consistency beats a shared import here;
  three modules already carry it.
- Bad documents are drawn from the three existing malformed builders plus a
  zero-byte file, cycled to reach 5 — so each of the three failure *layers* is
  represented in the batch rather than five copies of one shape.

## 3. Expanded goals

### G-1 — `parse -o` batch arithmetic (the plan's headline assertion)

A batch of N good + 5 bad documents must:

1. write **exactly N** `.xml` files — the number the plan asks for;
2. report **exactly 5** failures on stderr, each naming its own source path;
3. exit **1**;
4. print **no traceback**;
5. leave every written file **valid XML** — a survivor must not be truncated
   by its neighbour's failure.

Assertion 1 is the load-bearing one and the one with no current coverage:
§1.5's defect wrote 229 files for 233 sources while reporting success for all
233. Counting stdout mentions, as the existing test does, would not have caught
it.

### G-2 — the failure is isolated, not forgiven

- A bad document in **first** position must not prevent later documents writing.
- A bad document in **last** position must not retroactively affect earlier ones.
- The guard must hold for a document that fails **after** `_read` — i.e. in
  model building, rendering or validation — which is the §1.6 gap specifically
  (`_read` was already isolated before the fix). Exercised by monkeypatching
  `_render`, the way `test_cli.py::test_parse_isolates_a_failing_document` does,
  but at batch scale and asserting the written count.

### G-3 — the same arithmetic for `corpus`

`run_corpus` over the same mixed directory must report `total == N+5`,
`succeeded == N`, `failed == 5`, and `check() is None`. Every failed outcome
carries an error and no route. Multi-failure is the new part; the existing
tests all use exactly one.

### G-4 — resumability, stated honestly

Three assertions plus a documentation change:

1. **Idempotent** — running the same batch twice into one directory produces
   byte-identical files and the same file count. (Measured; see Q-2.)
2. **No suffix growth** — a re-run of URN-colliding sources does not accumulate
   disambiguation suffixes.
3. **Not cheap** — a re-run does the same work; nothing is skipped. Asserted by
   observing that every document is re-rendered on the second run.
4. `_write_bundle`'s docstring gains a short paragraph stating the re-run
   contract, next to the existing single-invocation paragraph it belongs with.

### G-5 — no traceback, ever, at batch scale

The predecessor's `test_no_invocation_in_this_module_ever_printed_a_traceback`
pattern, extended to the batch commands: for every degenerate and malformed
input, `parse -o` and `corpus` print no traceback.

## 7. Risks

- **Suite time.** 25 documents × parse × validate is the cycle's whole cost.
  Mitigated by a module-scoped fixture and by `--no-validate` on the tests that
  are not about validity. Budget: under 15 s added.
- **A test that passes vacuously.** Cycle 6's report flags this exact risk for a
  cycle that changes no `src/`. Mitigated by
  `test_an_all_good_batch_exits_zero` (the converse) and by asserting **exact**
  counts rather than "at least one".
- **The `_render` monkeypatch could mask a real guard removal.** Mitigated by
  also asserting the written count, not just the exit code: a removed guard
  changes how many files land, which a code-only assertion would miss.
