## 2. Root cause — verified, not inherited

The plan states the cause and a verified remedy. Per the skill's "verify, don't
trust", both were reproduced in this tree before any edit. **Both halves
confirmed**, and they are two independent mechanisms:

### 2.1 The summary line (`_count` → 0)

The module-scoped `bare_run` fixture runs the subset with `["-q", "-rs"]`. The
captured stdout from the failing baseline run, verbatim:

```
'\x1b[32m\x1b[32m\x1b[1m509 passed\x1b[0m, \x1b[33m131 skipped\x1b[0m\x1b[32m in 7.78s\x1b[0m\x1b[0m'
```

`_count` splits on whitespace and reads the token *before* `"passed"`. That
token is `'\x1b[1m509'`, not `'509'`, so `int()` raises and `_count` returns
**0** — which is why the assertion message reads `nothing ran in the bare
checkout` while the run in fact passed 509.

Measured directly:

```
args=['-q','-rs']              summary='\x1b[32m\x1b[32m\x1b[1m14 passed\x1b[0m…'
args=['-q','-rs','--color=no'] summary='14 passed in 0.13s'
```

### 2.2 The skip lines (`startswith("SKIPPED")` → no match)

A separate mechanism with the same cause. Measured against
`tests/unit/test_schema_matrix.py`, which genuinely skips in this tree:

```
args=['-q','-rs']               startswith SKIPPED: 0   contains SKIPPED: 2
   raw: "\x1b[33mSKIPPED\x1b[0m [2] tests/unit/test_schema_matrix.py:101: case N1 …"
args=['-q','-rs','--color=no']  startswith SKIPPED: 2   contains SKIPPED: 2
   raw: "SKIPPED [2] tests/unit/test_schema_matrix.py:101: case N1 …"
```

The line begins with `\x1b[33m`, so `startswith("SKIPPED")` never matches. This
is what fails `test_skips_carry_the_probe_diagnostic` (no reasons collected) and
`test_the_nested_assertions_are_the_ones_that_skip` (empty module set).

**Why it is environment-induced.** `pyproject.toml`'s `addopts` is
`-m 'not live'` — nothing forces colour. pytest decides by TTY/environment, so
the same commit is green where stdout is not a terminal and red where pytest
believes it is. That is precisely the "environment reason" §1.7 names.

### 2.3 Blast radius — one file

`test_bare_checkout.py:172` is the **only** place in `tests/` or `scripts/` that
runs pytest in a subprocess, and `_count` / `startswith("SKIPPED")` at lines
270–271, 291 and 342 are its only output parsers. Nothing else in the repository
parses pytest output. The fix touches exactly one file.

## 3. Reconciliation

Nothing here is blocking, so per the skill's Step 3 no question goes to the user:
the cycle text names its remedy, the remedy is verified, and the exit criterion
is a command with an objective result. The decisions below are mine, recorded
here rather than asked.

### N-1 — What "the harness's own parsing is exercised" means

The plan asks for an assertion that the parsing is exercised "so the next
formatting change fails loudly instead of silently reading zero". The failure
mode is specific and worth naming: **both broken parsers fail *falsily***.
`_count` returns `0`; the skip filter returns `[]`. A future formatting change
therefore degrades the harness toward vacuous green — or, as at this baseline,
toward an assertion failure whose message actively misleads (`nothing ran in the
bare checkout`, about a run that passed 509).

Guarding that needs two different things, and I am doing both:

1. **Direct unit tests of `_count`** against a real colourised summary string —
   the parser tested in isolation, where a regression is unambiguous.
2. **A guard on the live `bare_run`** asserting the parse of the real subprocess
   output actually found something, with a message that says *the harness is
   broken*, not *the parser is broken*. This is the part that catches a pytest
   output-format change, which no fixed test string can anticipate.

Deciding this myself rather than asking: it is internal test structure, which
the skill's Step 3 explicitly assigns to me.

### N-2 — Fix the parsers too, or only pass `--color=no`?

`--color=no` alone satisfies the exit criterion. I am **also** making `_count`
and the skip filters colour-tolerant, because the two defend different things:
the flag governs what *this* harness asks for, while tolerant parsing survives
someone later adding a colour-forcing option, a `PY_COLORS=1` in CI, or a pytest
default change. Neither is sufficient alone, and the belt-and-braces cost is a
few lines.

This is additive: it cannot make a currently-passing assertion fail, because
every string that parses correctly today still parses correctly after.

### N-3 — Where the new tests live

In `tests/regression/test_bare_checkout.py`, beside the harness they test. They
are tests *of the harness*, and separating them from it would leave a reader of
the harness with no local evidence it is self-checking.

## 4. Expanded goals

### G-1 — `--color=no` on the subprocess invocation

`_run_pytest` gains `--color=no`, placed in the **function** rather than at each
call site so no future caller can forget it. A comment records why, at the level
of detail the module's existing commentary sets.

### G-2 — Colour-tolerant parsing

- `_count` strips ANSI SGR sequences before tokenising.
- The two skip filters match on a colour-stripped line rather than the raw one.

A single module-level `_strip_ansi(text)` helper, applied at both sites.

### G-3 — The harness asserts its own parsing works

- `test_count_reads_a_colourised_summary` — `_count` against the exact
  colourised string this baseline produced.
- `test_count_reads_a_plain_summary` — the uncoloured form still reads.
- `test_count_is_absent_safe` — a word not present returns `0` (pins existing
  behaviour, so G-2 cannot change it).
- `test_the_harness_parses_its_own_subprocess_output` — on the live `bare_run`:
  the summary line parses to a non-zero total **and** the skip filter is
  non-empty, failing with a message that names the harness as the suspect.

### G-4 — No other change

No source under `src/` is touched. No golden moves. No existing assertion is
weakened, and the three currently-failing tests are fixed by repairing the
harness beneath them, **not** by relaxing what they assert.

## 8. Risks

- **The remedy hides a real failure.** If the bare run were genuinely broken,
  `--color=no` would turn a misleading red into a *correct* red, not green. The
  baseline traceback already shows the subprocess exiting 0 with 509 passed /
  131 skipped, and `test_suite_subset_passes_without_the_proposed_schemas`
  (which checks `returncode == 0`) passes today — so the bare run is healthy and
  E-1 genuinely means repaired, not silenced. Low.
- **Environment-dependence in the other direction.** These tests pass where
  pytest emits no colour, so a green result must be read as "green *here*". G-2's
  colour-tolerant parsing is what makes the result environment-independent, which
  is why N-2 does both. Low.
- **`--color=no` unsupported.** It is a stable pytest option and was exercised
  directly in §2. None.
